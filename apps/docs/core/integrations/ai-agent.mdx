title: "AI agent (Hermes)"
description: "Check whether tasks and bugs are ready for an AI coding agent, answer its questions, and Ship ready work to Hermes Agent, which opens a pull request."
---

The AI agent hands well-specified tasks and bugs to [Hermes Agent](https://github.com/NousResearch/hermes-agent), an open-source coding agent. It runs in a separate service, the **agent runner**, which you host next to Kaneo or on any machine that can reach it.

Every task and bug in a project with the agent turned on gets:

- an **AI readiness** bar with a score from 0 to 100,
- a panel with Hermes's **questions**, each with suggested answers, and **suggestions** you can add to the description,
- a **Ship** button once the task is ready. Hermes then implements it on a branch and the runner opens a pull request.

Kaneo itself never runs the model, a shell or git. Nothing changes for a project until an admin turns the agent on, and a single instance needs no extra services unless you run the agent.

## How it works

1. When someone creates or edits a task or bug, Kaneo queues a readiness check. Edits made within 30 seconds count as one. Tasks that come from an integration or an import, and drafts created together with a Feature or milestone, are checked when someone opens them. With **Check readiness automatically** off, checks run only when someone chooses **Check now**.
2. The runner asks Kaneo for work every few seconds. Kaneo never connects to the runner, so the runner can sit behind a firewall.
3. For a check, Hermes reads the repository without changing it. It scores the task against a checklist (goal, acceptance criteria, scope, reproduction steps and expected behaviour for bugs, constraints, how to verify) and lists the questions it can't answer from the task or the code.
4. Answering questions saves them as **decisions** and checks the task again right away. **Add to description** appends a suggestion to the description.
5. A task is **ready** when its score reaches the project's threshold and no blocking question is open. Editing it afterwards marks the check **outdated** until the next one finishes.
6. **Ship** queues the work. Hermes implements it on the branch the GitHub integration expects (`{slug}-{number}` by default), runs the tests the repository documents, and commits. The runner then pushes and opens the pull request, and Hermes comments on the task with the link. If Hermes needs a decision, it stops, and its questions appear in the panel.

Progress shows live on the task while Hermes works, and **Cancel** stops it. A later Ship of the same task continues the same branch and pull request.

## Set it up

You need permission to manage workspace settings.

### 1. Create a runner token

Go to **Settings → Workspace → AI agent** and choose **Create token**. Copy it right away: Kaneo shows it once and keeps only a hash. The page also shows the environment variables to give the runner. **Replace token** issues a new token and stops the old one at once, and a runner still using it abandons the run it's working on; **Revoke token** disconnects the runner.

### 2. Run the agent runner

The runner image bundles Hermes Agent, git and the GitHub CLI. With the Docker Compose setup, set these in your `.env` and start the `agent` profile:

```bash .env
KANEO_RUNNER_TOKEN=kar_...
AGENT_GH_TOKEN=github_pat_...
AGENT_OPENROUTER_API_KEY=sk-or-...
```

```bash
docker compose --profile agent up -d
```

Set the other [runner settings](#runner-settings) in `.env` the same way, with an `AGENT_` prefix: for example `AGENT_HERMES_PROVIDER=anthropic` and `AGENT_ANTHROPIC_API_KEY=...`. Empty ones keep the defaults, and nothing else in `.env` reaches the runner. The runner keeps its git mirrors and the runs in progress in its `/work` volume.

To run it anywhere else:

```bash
docker run -d --name kaneo-agent-runner \
  -e KANEO_API_URL=https://kaneo.example.com \
  -e KANEO_RUNNER_TOKEN=kar_... \
  -e GH_TOKEN=github_pat_... \
  -e OPENROUTER_API_KEY=sk-or-... \
  -v kaneo-agent-work:/work \
  ghcr.io/usekaneo/agent-runner:latest
```

Start the container as root, the default, not with `--user`: the runner sets up the container and then runs Hermes itself as unprivileged users, one for each run at the same time.

On Kubernetes, set `agentRunner.enabled` and `agentRunner.existingSecret` in the Helm chart, and other settings in `agentRunner.extraEnv`; see the comments in `values.yaml`. Don't set `runAsUser` or `runAsNonRoot` for the runner.

**Settings → Workspace → AI agent** shows the runner as **Online** once it polls.

### 3. Turn it on for a project

Open the project's **Settings → Integrations**, and choose **Configure** next to **AI agent (Hermes)**:

| Setting | What it does |
| --- | --- |
| **Use Hermes in this project** | Shows readiness on the project's tasks and bugs and lets members Ship them. Turning it off cancels the agent's queued work in the project. |
| **Check readiness automatically** | Checks tasks when they're created or edited. Turn it off to check only on request. |
| **Repository** | `owner/name` on GitHub. Leave it empty to use the repository of the project's GitHub integration. |
| **Base branch** | The branch Hermes starts from and pull requests target. |
| **Ready threshold** | The score, from 1 to 100, at which a task counts as ready. The default is 80. |
| **Instructions for Hermes** | Guidance Hermes gets with every task in the project, such as test commands. Hermes also reads `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md` and the README in the repository. |

Anyone who can edit a task or bug can answer its questions and Ship it.

## Runner settings

With Docker Compose, set these in `.env` with an `AGENT_` prefix, such as `AGENT_SHIP_CONCURRENCY`. `KANEO_RUNNER_TOKEN` keeps its name, Compose sets `KANEO_API_URL`, and the image sets `HERMES_UID` and `HERMES_GID`.

| Variable | Default | Description |
| --- | --- | --- |
| `KANEO_API_URL` | required | Kaneo's URL. `/api` is added when missing. |
| `KANEO_RUNNER_TOKEN` | required | The workspace's runner token. |
| `GH_TOKEN` | none | Pushes branches and opens pull requests. Without it the runner only checks readiness. |
| `OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `NOUS_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_API_KEY` | none | Model provider keys. Hermes uses the one for `HERMES_PROVIDER`. Compose passes on only these; for another provider, add its key to the runner's `environment` in a Compose override file. |
| `HERMES_MODEL` | `anthropic/claude-sonnet-5.5` | The model Hermes uses. |
| `HERMES_PROVIDER` | `openrouter` | The Hermes inference provider. |
| `GITHUB_HOST` | `github.com` | For GitHub Enterprise Server. The runner gives `GH_TOKEN` to git and to the GitHub CLI, which reads it as `GH_ENTERPRISE_TOKEN` there. |
| `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL` | `Hermes Agent` | The author of Hermes's commits. |
| `ASSESS_CONCURRENCY`, `SHIP_CONCURRENCY` | `2`, `1` | Runs at once of each kind. |
| `ASSESS_TIMEOUT_MS`, `SHIP_TIMEOUT_MS` | 10 minutes, 60 minutes | Longer runs are stopped and reported. |
| `ASSESS_MAX_TURNS`, `SHIP_MAX_TURNS` | `40`, `200` | Tool-call limit per run. |
| `SHIP_TOOLSETS` | `file,terminal,todo` | Hermes toolsets for Ship. Add `web` to let it read documentation online. |
| `HERMES_UID`, `HERMES_GID` | `10000` | The image's `hermes` user, which gets these IDs at startup. Hermes runs as users above it, one for each run at the same time: `HERMES_UID`+1 up to `HERMES_UID` plus `ASSESS_CONCURRENCY` plus `SHIP_CONCURRENCY`. With `HERMES_UID` set, the runner must run as root. |

One runner serves one workspace. Run another with its own token for each workspace.

## Security

Hermes runs commands that it decides on from task text, comments and repository content. Treat a runner like a CI job that anyone who can edit tasks can trigger.

- **Use a fine-grained GitHub token** limited to the repositories the agent works on, with **Contents** and **Pull requests** read and write access. Kaneo never stores it.
- **Hermes runs as a separate user.** The runner runs as root in its container and starts Hermes, and every git command in Hermes's checkout, as an unprivileged user, a different one for each run at the same time. That user can't read the runner's environment, which holds the GitHub and runner tokens, or the runner's git mirrors. Run users are separate from root, from the image's own `hermes` user and from each other, so none of them can read another user's process environment. No process gets the tokens on a run's behalf either: the image doesn't run the Hermes dashboard or its supervised gateway, which would run as the image's `hermes` user with the container's environment, and it runs Hermes's startup setup without the tokens. Hermes's own environment has neither token, and its config refuses `git push` and `gh` even in unattended mode.
- **Only the runner pushes, to the task's branch.** When Hermes finishes, its commits are packed into a git bundle as the run's user. The runner fetches that bundle into a fresh copy of the repository that only it can write, checks that the commits build on the branch the run started from, and pushes from there to the repository's GitHub URL. Hooks or git configuration that Hermes left in its checkout never run with the token.
- **Readiness checks are read-only.** Hermes gets file tools that can't write outside a scratch directory, and no shell or web access. Tasks synced from public issue trackers can contain prompt injection, which is why only a person's Ship starts code changes.
- **The container is the sandbox.** Ship runs Hermes without command approvals inside the runner container. Don't mount the Docker socket or host directories into the runner.
- **Each run starts fresh.** Every run gets its own clone and its own Hermes home, with its own sessions and memory, closed to the users of other runs. Hermes's temporary files go to the run's own directory, too. When the run ends, the runner kills every process of the run's user, including daemons a build started, deletes that user's files in the shared temporary directories and its shared memory and message queues, and deletes the clone and the home. Nothing a run starts or plants reaches a later run. Runs going on at the same time are closed to each other's files, but they share the container's network and `/tmp`, so treat the tasks one runner works on as one trust domain.
- **The runner must start as root.** Started as another user, with `--user` or `runAsUser`, it can't switch users, so it exits with an error rather than run Hermes where it could read the tokens.
- Secrets that match the runner's tokens or the provider keys listed in [runner settings](#runner-settings) are removed from the progress and assessments Kaneo shows.
- Review every pull request before you merge it.

To turn the agent off for the whole instance, set `DISABLE_AI_AGENT=true` on Kaneo. Its pages and routes then return 404, and runners can't claim work.

## Troubleshooting

- **Runner shows Offline**: check its logs. A `401` means the token was replaced or revoked. Create a new one and restart the runner.
- **The runner exits with "The runner must start as root" or "HERMES_UID is set, but the runner runs as uid …"**: the container was started as a non-root user, with `--user` or `runAsUser`. Start it as root.
- **The runner logs "credential isolation is off"**: it runs outside the image, without `HERMES_UID`, so Hermes runs as the runner's user and can read its tokens. Use the image.
- **Ship stays queued**: the runner may be offline, or have no `GH_TOKEN`, in which case it only checks readiness.
- **"Hermes failed: credentials or agent init failed"**: the provider key is missing or wrong for `HERMES_PROVIDER`.
- **A run failed after "The runner stopped reporting progress"**: the runner restarted twice during the same run. Ship the task again.
