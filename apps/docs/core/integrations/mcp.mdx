Kaneo supports the Model Context Protocol (MCP) in two ways:

1. **Built-in HTTP endpoint**: every Kaneo instance exposes `/api/mcp` out of the box. No extra setup, no extra process.
2. **Stdio package** ([`@kaneo/mcp`](https://www.npmjs.com/package/@kaneo/mcp)): the official Kaneo MCP package on npm, a local stdio server for clients that prefer stdio transport.

Both offer the same tools for managing workspaces, projects, project pages, tasks, Features and their documents, milestones, releases, test cases, time off, comments, and labels.

To work with Kaneo from a terminal or a shell script instead, use the [Kaneo CLI](/cli).

## Built-in HTTP endpoint

Every Kaneo API instance ships with a Streamable HTTP MCP endpoint. This is the recommended approach for self-hosted deployments.

Point your MCP client at:

```
https://your-kaneo-instance.com/api/mcp
```

With an OAuth-capable client, you will be redirected to Kaneo to sign in and explicitly approve the MCP client. After approval, all MCP tools run as your authenticated user.

The endpoint implements OAuth 2.1 with PKCE for authentication. Discovery metadata is available at:

- `/.well-known/oauth-protected-resource/api/mcp`
- `/.well-known/oauth-authorization-server/api`

The endpoint serves both MCP protocol eras without server-side sessions. Modern
`2026-07-28` requests are self-contained; 2025-era clients still send
`initialize`, but Kaneo does not issue a session ID. See [MCP protocol
reference](/core/integrations/mcp-stateless) for transport behavior, proxy
requirements, and request limits.

## Stdio package

The `@kaneo/mcp` package runs a local stdio MCP server and authenticates with Kaneo using device authorization. Use this when your MCP client requires stdio transport.

### Prerequisites

- Node.js 24 or newer
- A running Kaneo API
- Access to the Kaneo web app to approve device login

By default, self-hosted Kaneo allows both `kaneo-cli` and `kaneo-mcp` as device auth client IDs.

### Install and register

Use the recommended interactive installer:

```bash
npx -y @kaneo/mcp
```

The installer lets you choose where to register the server configuration:

- Cursor (user-wide)
- Cursor (project-level)
- Claude Desktop
- Custom JSON config path

You can also run the explicit install command:

```bash
npx -y @kaneo/mcp install --target cursor-user -y
```

Use `--help` to see all available targets and flags:

```bash
npx -y @kaneo/mcp install --help
```

### Point to a self-hosted instance

When generating config, pass your Kaneo base URL:

```bash
npx -y @kaneo/mcp install --target cursor-user -y --api-url https://kaneo.example.com
```

Or set it via environment variable:

| Variable | Description |
| --- | --- |
| `KANEO_API_URL` | Kaneo API base URL. Default: `http://localhost:1337`. A trailing `/api` is accepted and normalized. |
| `KANEO_MCP_CLIENT_ID` | Device auth client ID. Default: `kaneo-mcp`. |

If you override `KANEO_MCP_CLIENT_ID`, make sure it is included in [`DEVICE_AUTH_CLIENT_IDS`](/core/installation/environment-variables).

### Authentication flow

On the first tool call that needs Kaneo access, the MCP server:

1. Requests a device code from Kaneo
2. Prints a verification URL and user code
3. Opens the browser when possible
4. Polls until you approve sign-in
5. Stores credentials in `$XDG_CONFIG_HOME/kaneo-mcp/credentials.json`, or `~/.config/kaneo-mcp/credentials.json` when `XDG_CONFIG_HOME` is unset

## Available tools

Both the HTTP endpoint and stdio package expose the same 116 tools:

- Session: `whoami`, `list_workspaces`, `list_workspace_members`, `list_notifications`
- Teams: `list_teams`
- My work: `list_my_tasks`, `list_workspace_activity`
- Search: `search`
- Projects: `list_projects`, `get_project`, `create_project`, `update_project`, `update_project_details`, `list_project_columns`, `list_custom_fields`, `list_project_links`
- Project pages: `list_project_pages`, `get_project_page`, `create_project_page`, `update_project_page`
- Tasks: `list_tasks`, `get_task`, `get_task_by_ticket_id`, `create_task`, `duplicate_task`, `update_task`, `delete_task`, `move_task`, `update_task_status`, `update_task_assignee`, `update_task_estimate`, `update_task_due_date`, `list_task_activity`
- Triage: `accept_triage_task`, `decline_triage_task`
- Task details: `get_task_description`, `update_task_description`, `get_task_custom_fields`, `set_task_custom_field_value`, `list_task_external_links`, `create_task_external_link`
- Features: `list_features`, `archive_feature`, `set_task_feature`, `set_task_type`, `list_feature_issues`, `list_feature_activity`, `get_latest_feature_update`, `post_feature_update`
- Feature documents: `list_feature_documents`, `get_feature_document`, `create_feature_document`, `update_feature_document`
- Milestones: `list_project_milestones`, `list_milestones`, `get_milestone`, `create_milestone`, `update_milestone`, `delete_milestone`, `reorder_milestones`, `set_task_milestone`
- Releases: `list_releases`, `get_release`, `list_release_milestones`, `create_release`, `update_release`, `delete_release`, `set_task_release`, `move_unfinished_release_items`
- Test cases: `list_test_cases`, `list_feature_test_cases`, `list_release_test_cases`, `get_test_case`, `create_test_case`, `update_test_case`, `delete_test_case`, `list_test_case_comments`, `create_test_case_comment`, `update_test_case_comment`, `delete_test_case_comment`
- Time entries: `list_task_time_entries`, `get_time_entry`, `create_time_entry`, `update_time_entry`
- Time off: `list_time_off`, `list_time_off_requests`, `list_pending_time_off_requests`, `get_time_off_request`, `request_time_off`, `update_time_off_request`, `cancel_time_off_request`, `approve_time_off_request`, `decline_time_off_request`, `get_time_off_balance`, `list_time_off_balances`, `set_time_off_allowance`
- Public holiday calendars: `list_holiday_countries`, `get_holiday_calendar`, `set_holiday_calendar`, `list_holiday_calendar_requests`, `approve_holiday_calendar_request`, `decline_holiday_calendar_request`, `cancel_holiday_calendar_request`, `set_holiday_calendar_deadline`
- Comments: `list_task_comments`, `create_task_comment`, `update_task_comment`, `delete_task_comment`
- Labels: `list_workspace_labels`, `create_label`, `attach_label_to_task`, `detach_label_from_task`, `delete_label`
- Task relations: `create_task_relation`, `get_task_relations`, `delete_task_relation`

Every tool carries MCP annotations: `readOnlyHint: true` on reads and `false` on writes, and `destructiveHint: true` on the `delete_*` tools, so clients can run reads freely and ask before the rest.

`search` requires a `workspaceId` and searches that one workspace. It also takes an optional `type`. `tasks` returns Tasks and Bugs, and `features` returns Features. Features come back as `feature` results with `archived` and no status or priority. Comment and activity results carry the `taskId` and `taskType` of the item they belong to.

`list_task_activity` takes an optional `limit` (1 to 100) for the most recent entries; without it, it returns the whole feed.

Use `get_task_by_ticket_id` with a key such as `KAN-12` to fetch one task directly. If the same key identifies multiple accessible tasks, pass `workspaceId` or `projectId` to select one.

`list_project_columns` is worth calling first when setting a status: the column
slugs it returns are exactly the values `create_task` and `update_task_status`
accept. Likewise `list_workspace_members` resolves the user IDs the assignee
tools expect. Time entries have no delete endpoint on the API, so there is no
`delete_time_entry` tool.

`update_task`, `update_task_assignee` and `update_task_due_date` return 409 `TASK_ASSIGNEE_AWAY` when a start or due date they set falls on a day the assignee is away: approved [time off](/core/functional/time-off#task-dates) or a public holiday of their calendar. Only the dates a call changes are checked, or both when the work goes to someone else; pending requests never block, and planned work keeps its planned assignee until the next Apply. Dates are read as days in the `timeZone` the call passes (an IANA zone such as `Europe/Berlin`), else in the project's planning timezone, or UTC when it has none. The message names the dates, never the type of time off.

### Features

A [Feature](/core/functional/plan-and-execute-tasks#group-work-into-features) is a knowledge record. `list_features` supports project-scoped search, active/archived selection and pagination. `archive_feature` archives or unarchives a Feature without changing its child work. `create_task` with `type: "feature"` creates knowledge metadata and rejects planning fields. Feature resources return null planning values.

`create_task` accepts `customFields`, with field ids from `list_custom_fields` and each value as a string. With `type: "feature"` it also accepts `featureComposition`: milestones identified by your own `key`, existing Tasks/Bugs with no Feature to move in, title-only Task/Bug drafts placed by `milestoneKey`, and `unassignedReleaseId` for drafts without a milestone. The Feature and all of it are saved together, or nothing is.

`set_task_feature` links or clears a Task/Bug's Feature within its project; changing it clears the milestone. `set_task_type` supports Task ↔ Bug only. No API or compatibility relation promotes leaf work to a Feature. Feature duplication creates an empty record, and deletion retains its child work. Older `subtask` relations require an existing Feature context.

Features do not have relations. `create_task_relation` links Tasks and Bugs with `blocks` or `related`, and refuses a Feature on either end. `get_task_relations` lists a Feature's tasks only as deprecated `subtask` entries.

### Documents and descriptions

`get_project_page` and `get_feature_document` return the body in slices with `offset`, `totalLength`, `truncated` and `nextOffset`, plus the `revision`. `get_task_description` returns 32,768-character pages with a `version`; pass it back with `offset` to read on. `truncated` is false only when the result holds the whole text.

`update_project_page` and `update_feature_document` rename, append Markdown (`appendMarkdown`), or replace the whole `body`. A full replace needs the `expectedRevision` you read and fails with `DOCUMENT_CONFLICT` if the document changed since. Renames and appends use the current revision unless you pass one. `update_task_description` either appends Markdown or replaces the description, and a replace needs `expectedDescription`, the complete current text. These edits keep the attachments they remove.

Document writes return the metadata and `totalLength` instead of the body. `update_task_description` returns the task without its description, plus `descriptionLength`.

### Milestones

Milestone tools manage Feature-owned planning units with lead, workflow status, priority, release and dates. `list_project_milestones` returns paginated project summaries for scheduling without one request per Feature. `create_milestone` can link existing work with `taskIds` and create title-only Task/Bug drafts with `newTasks`, in the new milestone and its release; all of it is saved or nothing is. `set_task_milestone` changes membership within the Task/Bug's existing Feature. Lead changes require assignment permission; management requires the milestone permissions (`milestone:create`, `milestone:update`, `milestone:delete`). Milestone status and dates are read-only and derived from nonarchived linked Tasks/Bugs. All eligible work Done means Done; any active or completed work means In Progress; otherwise To Do, including empty milestones. Status ignores filters and release boundaries; progress keeps its existing counting rules.

### Triage

In a project with [triage members](/core/functional/triage), new Tasks and Bugs from anyone else start in the `triage` status. `list_tasks` returns them in `data.triageTasks`, never in columns or `plannedTasks`; pass `status: "triage"` to list only them. `accept_triage_task` moves one to To Do, or the first open column, and `decline_triage_task` archives it and posts the optional `reason` as a comment. Both notify the reporter. Only triage members can use them; with no triage members, holders of `project:update` can still clear waiting work. `update_task_status`, `update_task` and `move_task` refuse to set `triage` or to move work out of it.

### Releases

Releases hold milestones and Tasks/Bugs. Their summaries count Task/Bug execution, milestone execution and Feature knowledge groups separately. Historical charts remain Task/Bug-only.

`set_task_release` changes a Task/Bug's release. New work inherits its milestone's release only when omitted; an explicit release or null wins. Assigning existing unassigned work inherits the milestone release, while existing release choices remain. Updating a milestone's release moves only followers matching its old release, including null. Clearing/deleting membership preserves releases.

`move_unfinished_release_items` handles unfinished milestones and leaf work independently, leaving completed work in its original release. Release creation/edit requires project update permission; deletion and moving unfinished items also require update permission on tasks, bugs and milestones.

Test case tools manage a project's test cases: a title, preconditions (`description`), `steps`, `expectedResult` and a result `status` (`not_run`, `passed`, `failed`, `blocked`), linked to at most one milestone and one Bug of the same project. `list_feature_test_cases` lists those linked to a Feature's milestones; `list_release_test_cases` lists those whose milestone is planned for the release or whose Bug is in it and not archived. List rows leave out steps; `get_test_case` returns them. Management uses the test case permissions (`test_case:create`, `test_case:read`, `test_case:update`, `test_case:delete`), and linking also needs read access on the milestone or Bug. The comment tools list a test case's comments and add, edit or delete your own: reading needs `test_case:read`, writing needs `test_case:update`, and only a comment's author can edit or delete it.

### Time off

[Time off](/core/functional/time-off) is whole days, start and end inclusive, as `YYYY-MM-DD`. The type is `vacation`, `sick` or `public_holiday`. Days count as working days: Monday to Friday, except the member's calendar public holidays. The server's "today" is the UTC date.

- `list_time_off` lists who is away from `from` to `to`, both included, in a window of at most 366 days, with members' calendar holidays under `holidays`. Other members' entries contain only `id`, `userId`, `startDate` and `endDate`, and their holidays only `userId` and `date`; type, note, status, balance and holiday names stay with the person away and approvers.
- `request_time_off` always creates a pending request, an approver's own too. Pass `userId` to record time off for another current member. The dates need a working day (400 `TIME_OFF_NO_WEEKDAYS` otherwise), and overlapping the member's other pending or approved days returns 409 `TIME_OFF_OVERLAP`.
- `update_time_off_request` changes the type, dates or note; `note: null` clears it. Approvers can also edit approved time off, which stays approved. `cancel_time_off_request` keeps the request as history; the person away can cancel approved time off only until its first day is over, by the UTC date (409 `TIME_OFF_STARTED` after).
- `approve_time_off_request` and `decline_time_off_request` need the request's current `version`, so call `get_time_off_request` first. An edit since then returns 409 `TIME_OFF_CHANGED`, and a request that is no longer pending returns 409 `TIME_OFF_STATUS`.
- `get_time_off_balance` and `list_time_off_balances` return one balance per type under `types`, each counting working days per January–December year against that type's own allowance, with no carry-over. Weekday holidays of the member's calendar also count as used `public_holiday` days. `list_time_off_balances` also returns `defaultAllowances`. Going over an allowance is allowed: check `remainingDays` in a balance, or `overAllowanceDays` on a pending request, which uses the request's own type.
- `set_time_off_allowance` takes a `type`. Without `userId` it sets that type's workspace default (`vacation` 25, `sick` 10 and `public_holiday` 10 until set); with `userId` and a number it sets the member's override of that type, and with `userId` and `days: null` it clears it. An allowance applies to every year.
- `list_holiday_countries` lists the countries a member can pick as their public holiday calendar; with `country`, it lists that country's regions instead.
- `get_holiday_calendar` reads a member's calendar, or null, and its holidays in one year, weekends included. It also returns `calendarChosen`, `pendingRequest` (a change waiting for approval, with its `id` and `version`, or null), `holidayCalendarDeadline` and `nextChangeNeedsApproval`.
- `set_holiday_calendar` sets a member's calendar to a `country` and optional `region`, or clears it with `country: null`. An unknown country or region returns 400 `TIME_OFF_HOLIDAY_CALENDAR_UNKNOWN`. A member's first choice, `country: null` included, applies at once on or before the workspace's [setup deadline](/core/functional/time-off#the-setup-deadline), a UTC day that counts, or at any time without one. Every later change by the member, and any choice after the deadline, returns `status: "pending"` with `pendingRequest`. A new request notifies approvers; sending another calendar while one waits updates that request and increases its `version` without notifying anyone. Changes by approvers, for themselves or another member, apply at once with `status: "applied"`, and applying the calendar a member asked for approves their request. Applied calendar holidays count as approved time off without requests, planned work skips them, and plans that include the member become outdated. Members can still request `public_holiday` time off for days the calendar leaves out, such as bank holidays.
- `list_holiday_calendar_requests` lists current members' calendar changes waiting for approval, oldest first, each with the calendar asked for (null for no calendar) and `currentCalendar`. `approve_holiday_calendar_request` and `decline_holiday_calendar_request` take the `requestId` and the `version` you reviewed; a change by the member since then returns 409 `TIME_OFF_CHANGED`, and a request that is no longer pending returns 409 `TIME_OFF_STATUS`. Approving applies the calendar at once, or returns 400 `TIME_OFF_HOLIDAY_CALENDAR_UNKNOWN` if the holiday data no longer has it. The member is notified of either decision, unless they made it themselves.
- `cancel_holiday_calendar_request` withdraws a waiting change, your own or, for approvers, anyone's; sending your current calendar again with `set_holiday_calendar` withdraws your own too. Nobody is notified.
- `set_holiday_calendar_deadline` sets the workspace's setup deadline as `YYYY-MM-DD`, or removes it with `deadline: null`. Changes already waiting stay as they are.
- Holiday calendar requests show the country and region only to the member and to approvers; notifications and live updates never carry them.
- `list_holiday_countries`, `get_holiday_calendar`, `list_time_off`, `list_holiday_calendar_requests`, `approve_holiday_calendar_request` and `decline_holiday_calendar_request` take an optional `lang`, such as `de`, for holiday, country and region names.

Viewing the team needs `time_off:read`. Listing holiday countries and reading your own calendar need any time-off permission. Requesting, editing or cancelling your own requests, setting your own holiday calendar, and withdrawing your own calendar change need `time_off:create`. Approving, declining, recording time off for others, reading other members' requests, balances and holiday calendars, setting allowances and the setup deadline, listing and deciding holiday calendar changes, and setting other members' holiday calendars need `time_off:approve` and workspace membership.

### Teams

`list_teams` takes a `workspaceId` and returns the workspace's [teams](/core/functional/teams) by name, each with its `members` (`id`, `name`, `email`, `image`) and linked `projects` (`id`, `name`, `slug`, `icon`). Any workspace member can call it. Linked projects you can't access are left out. Members of a team can open its linked projects even when their own project access is limited to selected projects. The MCP server only reads teams; create and change them on the **Teams** page or through the API.

### Project links

`list_project_links` takes a `projectId` and returns the links in the project's [Resources](/core/functional/plan-and-execute-tasks#project-home), each with its `id`, `title`, `url`, and `position`, in the order people arranged them. Anyone with access to the project can call it. The MCP server only reads links; add and change them on the project's **Overview** or through the API.

## Debugging

To run the stdio server directly:

```bash
npx -y @kaneo/mcp serve
```

When running from source in this monorepo:

```bash
pnpm --filter @kaneo/mcp run build
pnpm --filter @kaneo/mcp run start
```
