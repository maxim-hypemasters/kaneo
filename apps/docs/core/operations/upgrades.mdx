Kaneo runs database migrations when the API starts. An upgrade can change your database as well as the application, so prepare a recovery point before changing the image.

## Before you upgrade

1. Read the [release notes](https://github.com/usekaneo/kaneo/releases) between your current and target versions.
2. Record the current image tag or digest and keep a copy of your Compose file and environment files.
3. Create a [database and file backup](/core/operations/backups), and check that you can restore it.
4. Choose a short maintenance window. Try the new release against a restored copy first when the change is substantial.

Do not change the PostgreSQL major version as part of an ordinary Kaneo image update. A database major upgrade needs its own migration procedure.

## Docker Compose

In the Compose setup from this guide, set `KANEO_IMAGE_TAG` in `.env` to the release you chose. If your Compose file hardcodes the image tag, edit that instead. Pulling an image does not restart the running container.

```bash
docker compose pull kaneo
docker compose up -d kaneo
docker compose ps
docker compose logs --tail=100 kaneo
```

## drim

Run `drim upgrade` from the deployment directory. It pulls the images selected by your existing Compose file. If those use `latest`, that means the newest published images. Review the file before running it.

Older two-container deployments need the [layout migration](/core/installation/drim-migration); upgrading images does not rewrite their Compose file.

## Check the result

- Request `/api/health` and confirm the container becomes healthy.
- Sign in, open an existing project, and create a test task.
- Open the same project in another browser session and check a status change appears.
- Upload and reopen an attachment if storage is configured.
- Check email and the integrations your team uses.

Keep the backup until you are satisfied with the result.

## If the upgrade fails

Capture the failing container logs and stop the new application container with `docker compose stop kaneo` while you investigate.

Do not assume an old image can read a newly migrated database. Unless the release explicitly supports that downgrade, recover using the previous application image plus its matching database and file backup. Follow [Backups and recovery](/core/operations/backups), and account for any work created since the backup. When a release has its own way back, the [upgrade notes](#upgrade-notes) describe it.

Never use `docker compose down -v` as an upgrade or troubleshooting step. It removes the named data volumes.

## Upgrade notes

### Feature milestones

The milestone migration adds a feature-owned table and a nullable milestone link to work items. Existing work starts without a milestone. It does not alter item types, Feature or Release membership, release-progress baselines, or historical totals. Apply the migration before serving milestone-capable code; the API migrates before accepting requests at startup.

The milestone date-range migration preserves each existing target date as its end date and starts with no start date. Use matching API and web builds after applying this migration. Existing milestone links, progress, and release history remain unchanged.

When updating multiple instances, update all API instances before using milestones so older code cannot change Feature membership without clearing a milestone. Verify milestone creation, task assignment, filtering, progress, and cross-window updates after the upgrade. Keep the matching pre-upgrade database backup for recovery.

### Bug task type

Kaneo adds **Bug** alongside Task and Feature in the existing task model. Apply the database migration before allowing Bug writes. The API runs it before serving requests at startup; when updating several API instances, update all of them before creating or converting Bugs because older servers do not understand the new type.

The migration expands the task hierarchy constraint and updates release progress tracking to include Tasks and Bugs. It does not change any existing item's type, rewrite recorded progress, seed another baseline, or backfill history. Task-to-Bug conversions keep feature and release membership and leave progress totals unchanged. Other import providers continue creating Tasks; a label named “bug” does not change an item's type.

After upgrading, create a Bug, filter a project by **Type**, and convert the Bug to a Task and back. Check that its feature and release stay selected and that the release totals remain the same. Native task exports and connected Kaneo imports preserve explicit Task, Bug, and Feature types; files without a type field default to Task.

To roll back to a version without Bug support, restore the matching application image and database backup. An older API can reject responses containing Bugs and cannot safely operate on them. Keep the backup until the new creation, filtering, and conversion flows have been checked.

### Project releases

Kaneo added [releases](/core/functional/releases) to projects. The database migration only adds things: a `release` table and an empty `release_id` column on tasks. Existing tasks start with no release, and no other data changes.

During a rolling update, older API servers keep running next to newer ones for a while, for example with several Helm replicas. An older server doesn't know about releases:

- It can't move a task that's in a release to another project. The database refuses the move and the server returns an error. Try again once every server runs the new version.
- Tasks it adds to a feature don't take the feature's release. The same goes for subtask links it writes, which the next start turns into feature links.
- When it duplicates a task, the copy has no release.
- It shows release names in task activity and search without hiding them from members who can't see the release's project.

After the update, check the release of any task that joined a feature while the update ran.

To go back to a version without releases, take every task out of its release first, and remove the release names from task activity. Otherwise the older version can't move those tasks to another project, and it shows those names to members who can't see the release's project.

1. Stop every Kaneo API instance that uses the database, for example with `docker compose stop kaneo`. With the Helm chart, scale the Kaneo deployment to zero replicas.
2. Make a [database backup](/core/operations/backups).
3. Take every task out of its release:

   ```bash
   docker compose exec -T postgres sh -c \
     'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "UPDATE task SET release_id = NULL;"'
   ```

   With a managed database, run `UPDATE task SET release_id = NULL;` with `psql` against it.

4. Remove the release names from task activity:

   ```bash
   docker compose exec -T postgres sh -c \
     'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
   UPDATE activity
   SET event_data = event_data - 'projectId' - 'oldReleaseName' - 'newReleaseName'
   WHERE type = 'release_changed';
   SQL
   ```

   With a managed database, run the same `UPDATE` with `psql` against it. The entries stay in each task's activity without naming the release.

5. If the earlier version also predates features, [undo the feature conversion](#subtasks-become-features) now as well: run its script and remove the feature titles from task activity.
6. Set `KANEO_IMAGE_TAG` back to the earlier version and start it with `docker compose up -d kaneo`. With the Helm chart, run `helm upgrade` with `kaneo.image.tag` set to the earlier version, and scale the deployment back up.

The releases themselves stay in the database, and the older version ignores them. If you upgrade again later, they come back without their tasks.

### Subtasks become features

Kaneo replaced subtasks with [features](/core/functional/plan-and-execute-tasks#group-work-into-features): a feature is a task that groups other tasks, one level deep. When the API starts on a version with features, it converts existing subtasks for you:

- A top-level task with subtasks becomes a feature, and its subtasks, at any depth, become its tasks.
- Links that don't fit, such as a second parent, a link between two levels below the feature, or a link to another project, become related relations.
- Before changing anything, Kaneo copies every converted subtask link to the `legacy_subtask_relation` table. Keep that table: the undo script below needs it.

The conversion runs on every start. Subtask links that an older server writes during a rolling update are converted on the next start. An older server can also move a task away from its feature's project; the next start takes that task out of the feature and keeps a related link between the two in its place. Until every server runs the new version, an older one shows feature titles in task activity and search without hiding them from members who can't see the feature's project. If a project can't be converted, the log says so, its subtasks stay as they are, and the server still starts. Kaneo tries that project again on the next start.

Older versions of the CLI, the MCP package, and `@kaneo/planka-import` still send subtask links. They keep working: each one becomes a feature link. A link that features can't hold, such as one to a task in another project, or one that would put a feature into a feature, is refused with an error.

After the upgrade, open a project that used subtasks and check that its features and their tasks look right.

To go back to an earlier version, undo the conversion first. `apps/api/src/migrations/feature-hierarchy-undo.sql` in the Kaneo source does that. It is not in the Docker image, so take it from the source of the release you upgraded to.

1. Stop every Kaneo API instance that uses the database, for example with `docker compose stop kaneo`. With the Helm chart, scale the Kaneo deployment to zero replicas.
2. Make a [database backup](/core/operations/backups).
3. Run the script once:

   ```bash
   docker compose exec -T postgres sh -c \
     'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
     < feature-hierarchy-undo.sql
   ```

   With a managed database, run the same file with `psql` against it.

4. Remove the feature titles from task activity. Versions before features show them to every member who can open the task, even one who can't see the feature's project:

   ```bash
   docker compose exec -T postgres sh -c \
     'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
   UPDATE activity
   SET event_data = event_data - 'projectId' - 'oldFeatureTitle' - 'newFeatureTitle'
   WHERE type = 'feature_changed';
   SQL
   ```

   With a managed database, run the same `UPDATE` with `psql` against it.

5. Set `KANEO_IMAGE_TAG` back to the earlier release and start it with `docker compose up -d kaneo`. With the Helm chart, run `helm upgrade` with `kaneo.image.tag` set to the earlier release, and scale the deployment back up if it is still at zero.

The script brings back the subtask links from before the upgrade, including the ones that were kept as related relations. Tasks added to a feature since then become subtasks of it too, and every feature becomes a plain task again. A task taken out of its feature after the upgrade gets its old parent back. Other changes made since the upgrade are kept. Once the links are back, the script empties `legacy_subtask_relation`. If you upgrade again later, Kaneo converts the subtasks again and backs them up afresh, so the script can undo that upgrade too.
