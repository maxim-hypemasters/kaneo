---
title: "Releases"
description: "Plan what ships together, with a start date, a code freeze, and a submission date."
---

A release is a named plan for a project, such as “2.4,” with three dates: when work starts, when changes stop, and when it ships. It holds milestones and Tasks/Bugs of that project, much like a sprint or a cycle in other tools. Use one when a group of work has to be ready by the same day.

Each Task, Bug, or Milestone is in one release at most, and only in a release of its own project. Bugs follow the same membership and milestone-following rules as Tasks. Counts labeled **Tasks** include both Tasks and Bugs.

## Open Releases

Expand a project in the sidebar and choose **Releases**. On phones, open the sidebar drawer first. You can also press **G** then **R** in a project, or choose **Go to releases** in the command menu.

The overview is a timeline with future releases above active releases and past releases below them. Within each phase, the latest start date comes first. The left rail shows each release's submission date at its top corner and highlights active releases; row spacing follows the content rather than a proportional calendar scale.

Each compact row shows the release's name, phase, Task/Bug completion percentage, and completed/total count. Active releases—**In progress** and **Code freeze**—always show their **Predicted**, **Started**, and **Completed** history chart, including the start, code freeze, submission, and today markers, plus Feature and milestone counts. Select the release name to [open its detail page](#follow-a-release).

Every active release shows its chart, including when several releases overlap. Upcoming and past releases stay compact; if none are active, all rows are compact. This updates automatically when dates change or the viewer's local day changes. Submission day remains active. History loads only for active releases, and chart loading or retry states do not hide the list.

## The three dates

| Date | What it means |
| --- | --- |
| **Start** | The first day of work. Marked with a flag. |
| **Code freeze** | The day changes stop, before the release ships. Marked with a snowflake. |
| **Submission** | The day the release ships. Marked with a paper plane. |

The dates must run in order: start, then code freeze, then submission. Two or all three can be the same day, which suits a quick fix.

The dates are calendar days without a time, so everyone sees the same days wherever they are. A release's phase comes from those dates and today's date on your device:

| Phase | When |
| --- | --- |
| **Upcoming** | Before the start date |
| **In progress** | From the start date until the day before code freeze |
| **Code freeze** | From the code freeze date through the submission date |
| **Past submission** | After the submission date |

The phase and countdown change at midnight on your device. Nothing else happens on these dates: tasks don't move or change status on their own. When a release is over, you decide what to do with any [unfinished work](#move-unfinished-work).

## Create a release

1. Choose **New release** on the Releases page, or **Create release** in the command menu while you're in the project.
2. Enter a **Name**. It must be different from the project's other releases.
3. Pick the **Start**, **Code freeze**, and **Submission** dates.
4. Add a **Description** of what the release delivers, if that helps.
5. Choose **Create release**.

When the project already has releases, the dialog suggests dates that start the day after the latest submission, or today if that day has passed, and keep that release's lengths. Change them as needed. Each date picker only offers days that keep the dates in order.

## Edit or delete a release

To change a release's name, dates, or description, open the actions menu on its row in the list, or open the release, and choose **Edit release**. Choose **Save** to apply the change. Its phase updates at once.

To delete a release, choose **Delete release** in the same menus and confirm. Its milestones and tasks stay in the project without a release, and each one's activity records that it left the release. A deleted release can't be restored: to get it back, create it again and put the work back in it.

## Put work in a release

- **In a Task/Bug or Milestone:** select **Release** in its properties and choose a release or **No release**. Features have no release property.
- **When creating work:** choosing a milestone uses its release unless you explicitly choose another release or **No release**. New Features never inherit a release.
- **From a release:** new Tasks and Bugs start in that release. **New feature** creates a knowledge record without planning fields.

Opening a Feature from a release also preselects that release when you create a milestone, including after opening the Feature in its full-page view. Choose another release or **No release** to override the suggestion. Existing milestones keep their own release when edited.

From a release's **New** menu, choose **Link existing milestone** or **Link existing tasks or bugs** to add existing work. Search, select items across pages, then choose **Link selected**. Each row shows its current release or **No release**. Work from another release moves into the open release; already assigned items are omitted. Completed Tasks/Bugs and empty milestones are available, while archived Tasks/Bugs are excluded.

Linking a Task/Bug changes only its release, preserving its Feature and milestone. Linking a milestone applies the follower rules below, keeping explicit child release overrides. Linking requires **Edit tasks**, independently of permission to create work. If an item cannot be linked, successful assignments remain saved and the remaining selection can be retried or removed.

## How tasks follow their milestone

- New Tasks/Bugs inherit their milestone's release when the release is omitted. Explicit values, including none, win.
- Assigning existing work to a milestone inherits its release only if the work currently has no release. Choosing a milestone never changes its Feature.
- Changing a milestone's release moves linked Tasks/Bugs whose release equals its previous release, including none. Work assigned to another release stays there.
- Clearing or deleting a milestone preserves child releases. Feature deletion also preserves child work and planning fields.

For example, a milestone in 2.4 has two Tasks in 2.4 and a Bug explicitly deferred to 2.5. Moving the milestone to 2.6 moves the two Tasks, while the Bug stays in 2.5. New work inherits 2.6 unless a release is chosen explicitly. Task/Bug duplication and Task ↔ Bug conversion preserve release membership. Moving work to another project clears it.

Each release change appears in the Task/Bug activity; milestone release changes appear in its owning Feature's history. Creation records only the initial creation.

## Follow a release

Select a release's name in the overview to open its page. **All releases** takes you back.

The page shows the release's phase, countdown, and description, then one **Progress over time** chart with its start, code freeze, submission, and today marked on the same timeline. The dates and feature, task, and unfinished counts appear alongside the chart, which tracks its tasks by day:

- **Predicted** is a straight dashed guide from zero at the start to the current task count at code freeze. It shows the steady pace needed to finish that scope by code freeze, rather than estimating future work from past activity. Its legend shows the expected count and percentage for today. Changing the release's task count updates the guide.
- **Started** includes tasks in workflow columns after the first unfinished column, including In Review and Done. Completed tasks stay included. Planned and archived tasks don't count as started.
- **Completed** counts tasks in columns with **Done** turned on.

The task count includes Tasks and Bugs, including archived ones; features don't add to it. Changing a Task to a Bug or back leaves the totals unchanged. The chart uses your device's time zone. Smooth curves connect the recorded daily totals for Started and Completed; tooltips show the exact counts for each day. Hover or tap a day to see its expected, started, and completed counts, or focus the chart and use the arrow keys. **Home** and **End** jump to the first and last recorded day. Started and Completed have no future values, while the Predicted guide runs to code freeze. Its expected count stays at the full scope after code freeze. When start and code freeze are the same day, the guide is vertical and that day expects the full scope.

History begins when progress tracking becomes available on your instance; a shaded gap marks earlier dates whose progress is unknown. The Predicted guide still covers that period because it describes the plan, independently of recorded activity. Editing dates doesn't invent earlier history. Changes after submission still appear, while days with no further change don't keep stretching a past release's chart.

Below the chart is the release's work:

- Feature knowledge headings for visible release work or explicitly planned milestones.
- Milestones assigned to the release, including empty ones, and milestone groups containing visible release work.
- **Tasks without a feature** last.

In each group, unfinished items come first and finished ones are dimmed below them. Archived tasks aren't listed. When some of a feature's tasks are in another release, or in none, its group says how many, such as “2 more tasks outside this release.” Select an item to open it in the task panel.

Each Feature header shows a completion percentage and completed/total count for its visible Tasks and Bugs in this release. Completion follows workflow columns marked **Done** and does not imply a Feature workflow status. An empty Feature shows **0% · 0/0**.

When a Feature has milestones, its work is grouped under those milestones in their manual order, with **No milestone** last for unassigned work. Empty milestones explicitly assigned to the release also appear. Each group shows its completion counter and progress diamond alongside its read-only milestone status. Status uses all nonarchived linked work across releases, while these counters use visible work in this release. Select its title to open the milestone panel. Features without milestones keep a flat list.

These row counters exclude archived work and work in other releases. The Feature window and its milestone overview keep their full ownership counts, while the release's overall totals and historical chart continue including archived work.

Releases, their progress, and their tasks update for everyone who has the project open, without reloading.

## Move unfinished work

When a release reaches its code freeze or its submission date with work left, move that work to the next release or out of releases altogether:

1. Open the release and choose **Move unfinished…**. From code freeze on, while work is left, the release's page highlights it.
2. Under **Move to**, pick another release or **No release**. Kaneo suggests the release that starts next, or **No release** when there's none.
3. Check how many items will move, then choose **Move items**.

Unfinished means not archived and not in a column with **Done** turned on in the project's [workflow](/core/functional/configure-workflows). Planned tasks in the backlog count as unfinished.

Each item moves on its own. Unfinished milestones and Tasks/Bugs are handled independently, so completed child work stays in the release it shipped in. Each moved item records the change in its activity.

## Find a release's work

- **Filter:** in **Tasks** or **Backlog**, choose **Filter**, then **Release**, and pick one or more releases, or **No release** for work that isn't in one. Switch **is** to **is not** to hide them instead. The filter applies to every layout. A saved filter whose release was deleted shows **Unknown release**. See [Find and filter work](/core/functional/plan-and-execute-tasks#find-and-filter-work).
- **Gantt:** the Gantt chart marks each release's three dates with lines, and its labels open the release. See [Calendar and Gantt](/core/functional/calendar-and-gantt#releases).

## Who can do what

| Action | Permission | Default roles |
| --- | --- | --- |
| See releases and their progress | Access to the project | Everyone, including viewers |
| Create or edit a release | Manage projects | Admin, Owner |
| Delete a release | Manage projects and edit tasks | Admin, Owner |
| Put Tasks/Bugs and milestones in a release | Edit tasks | Member, Admin, Owner |
| Move unfinished work | Edit tasks | Member, Admin, Owner |

These are the starting roles; an admin can [change them](/core/functional/collaborate-with-team#choose-a-role). Controls you can't use are hidden, and the same rules apply to API keys, the CLI, and MCP clients.

## Use releases from other tools

The [Kaneo CLI](/cli/reference) and the [MCP server](/core/integrations/mcp) can list, create, edit, and delete releases and set a task's release. The API's [endpoint reference](/api-reference/introduction) lists the routes under **Releases**.

Release summaries count milestone execution totals separately from Feature knowledge groups. The historical chart remains Task/Bug-only: editing milestone metadata alone does not create history events.
