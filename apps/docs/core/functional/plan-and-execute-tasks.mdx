Open a project and choose **Tasks**. To change how the same work is displayed, open **Display** at the top right and pick a layout: **Board**, **List**, **Calendar**, or **Gantt**.

Most actions have a keyboard shortcut: for example **C** creates a task, **G** then **I** opens your inbox, and **⌘B** switches between Board and List. Press **?** (or **⌘/**, **Ctrl+/** on Windows and Linux) anywhere to see and search every shortcut.

## Add a task

Choose **New** and then **New task**. On the board, the **+** control in each column opens the same menu and keeps that column selected. Home, project views, the backlog, releases, and Feature task sections offer **New task**, **New feature**, and **New bug** through the same creation menu. Give the item a title that describes the work, then open it to add details.

A title such as “Fix the mobile navigation” is easier to act on than “Mobile issues.” Use the description for context, links, and a checklist of smaller steps.

### Track a bug

Choose **New → New bug**, or choose **New bug** in the command menu. You can also select **Bug** in the creation window's **Type** selector. The **C** shortcut still starts a Task. In a Feature's task section, **New task** and **New bug** keep the quick inline title entry.

Bugs have the same properties, workflow, numbering, and actions as Tasks, with their own permissions: a role can report and edit bugs without being able to create tasks, or the other way round. A bug icon identifies them on cards, rows, calendars, Gantt, My Work, public boards, and search. A Bug can belong to a Feature and a Release. Bugs count as tasks in feature progress, release totals, and release progress charts.

To change an existing item's classification, open **Type** in its properties or use its card or row's conversion menu. Converting between Task and Bug keeps the same item, including its feature, release, comments, attachments, labels, dates, and history. Features have a separate knowledge role and cannot be converted to or from Tasks/Bugs.

## Move work on the board

Use [Feature milestones](/core/functional/milestones) to break a Feature into smaller stages. Select a milestone in the Feature sidebar to open its filtered Issues tab, or assign it from the Task/Bug's properties after selecting its Feature.

Drag a task to another column when its status changes. You can also change its status inside the task.

## Find and filter work

Use the search icon, or press ⌘F (Ctrl+F on Windows and Linux), to find Tasks, Bugs and Features by title, description, or number, and Feature documents by title or text. Features have their own **Features** group, with archived ones marked **Archived**. Choosing a document opens it in its Feature. Choosing a comment or activity opens the item it belongs to; for a Feature, that is its **Activity** tab. The full search page lists matching Features above Tasks and Bugs.

Use **Filter** to narrow the view by type, status, assignee, priority, labels, release, due date, or custom fields. Hover a property to pick its values, or type in **Add filter…** to search every value at once. Each filter appears as a chip above the tasks:

- Click the operator, such as **is**, to switch it to **is not** and hide matching tasks instead.
- Click the values to change them.
- Choose **×** to remove the filter, or **Clear all** to remove every filter.

Filters are saved for each project and apply to every layout. The count next to **Tasks** shows how many tasks match. If a task seems to have disappeared, clear your filters and check the backlog before creating another one.

The execution **Type** filter offers Task and Bug, with counts for each. Features are found through the dedicated library. Selecting more than one includes any selected type; other filters still apply. Use **is not** to exclude the selected types. Projects with older saved filters initially include all types. Filtering changes the visible items, while feature and release progress continue to count all their work.

Open **Display** to sort tasks and choose which details appear on cards and rows. Filled custom fields show as small chips on cards and rows; hover one to see the field name. Under **Fields**, turn off any field you don't want there. These choices are saved in your browser and only affect your view.

## Add the details people need

Open a task to edit its description and properties. Use **Open in full page** from the task panel when you want more space.

### Write a description

Feature, Task, and Bug descriptions open in reading mode. Click the description to start editing, then choose **Save** to publish it or **Cancel** to restore the saved version. You can also focus the description and press Enter to edit. Leaving with unsaved edits asks for confirmation. Save failures keep your draft available to retry. If someone else changes the description, review the saved version before choosing which text to keep.

Use the compact toolbar for headings, bold, italic, lists, and links. **Insert** offers checklists, tables, quotes, code blocks, images, files, and embeds. You can also type `/` to insert a block or use Markdown shortcuts. Tables have row and column controls, and images can be resized.

Choose **Expand document** for fullscreen reading or writing. Returning to the description keeps your draft and undo history. In creation forms, the description stays in the form until you create the Feature, Task, or Bug. Uploaded draft files become part of an existing description when you save it.

- **Assignee:** choose the person responsible for the next step. Clear it to leave the task unassigned.
- **Priority:** show what needs attention first. A task can have no priority.
- **Estimate:** enter total effort as `1d`, `4h`, `3w`, or a combined value such as `1d 4h`. A day is 8 hours and a week is 40 hours. Logged time reduces remaining effort. Start and finish dates come from the plan: open the release and choose [Plan release](/core/functional/calendar-and-gantt#estimate-and-plan-work) to review and apply them, or [move the work in Gantt](/core/functional/calendar-and-gantt#move-work). You can also set **Start** and **Due** by hand in the task's properties, from a card's right-click menu, from the bulk bar, or with **Shift+D**; dates set by hand take planned work off its estimate until the next Apply of its release.
- **Labels:** group related work across projects. Removing a label from one task does not delete the workspace label.
- **Release:** put the task in one of the project's [releases](/core/functional/releases), or choose **No release**. In an open task, **Shift+C** changes it.
- **Comments:** ask questions and record decisions where everyone following the task can find them.

Use the attachment button, paste, or drag a file into the editor to add supporting material. Images appear inline; other files appear as attachments. On self-hosted instances, an operator must [configure file storage](/core/installation/object-storage-and-image-uploads) first.

## Project home

Clicking a project's name in the sidebar, in search, or with a project shortcut opens its home page. **Tasks**, **Features**, and **Releases** in the sidebar still open those views, and **Tasks** returns to the layout you used last. The home page has two tabs, and the selected tab and open document are part of the URL.

- **Overview** shows the project's name and description. People with project-update permission edit them in place, and changes save as they type, as in the project's general settings.
- **Documents** lists the project's own pages and, below them, the documents of every active Feature grouped under that Feature. Feature documents keep their place and order; open one to edit it as you would on the Feature, or use the arrow next to the Feature to open it.

Project pages nest: any page can have sub-pages. **New page** adds a page at the top level, and **Add sub-page** in a page's menu adds one inside it. Drag a page by its handle to reorder it; drag it right to nest it under the page above, or left to move it out. **Move to…** in the menu does the same without dragging: choose **Top level** or a parent page, and the page moves there with its sub-pages, after the pages already in place. Pages open full screen and save automatically, like Feature documents, including uploads and the review when someone else saves first. Deleting a page also deletes its sub-pages and their uploads; the confirmation says how many sub-pages will go.

Project pages follow the same permissions as Feature documents: reading needs task-read permission, creating, editing, and moving pages needs task-update permission, and deleting needs task-delete permission. Changes appear for everyone viewing the project without a reload.

## Group work into features

A Feature is a durable knowledge record for a part of your product. Keep its documentation, labels, custom fields, resources, comments, implementation history, milestones, and linked Tasks/Bugs together. Features retain their identifiers and links but have no workflow status, priority, assignee, start/end dates, or release.

### Find and create Features

Open the project's **Features** library to search its active or archived Features. Rows show a description preview, labels and milestone count. Use **New → New feature**, the library's creation action, or **New feature** in the command menu. Features stay discoverable in search (in their own **Features** group), the Feature picker and task links, while execution boards, backlog, lists, Calendar and My Work show Tasks and Bugs.

The **New Feature** popup keeps its title, description, labels, custom fields and attachments. Its **Milestones** section adds ordered drafts with a title, Milestone Lead, priority and release. Status and dates come from linked work after saving. Each milestone card has a **Work** area: use its **New** menu to add title-only Task or Bug drafts directly to that milestone. To move a new draft, remove it and add it in the destination card.

Activate the shared search field below the milestone cards to find existing nonarchived Tasks/Bugs without a Feature, including completed work. Results stay open while selecting or paging and close when you leave the picker or press Escape. Search and selections are retained. Selected work starts in **No milestone**, where its milestone selector assigns it to a card. Each card shows its existing selections and new drafts together; to reassign existing work, remove it from the card and select it again. Removing a milestone with new drafts asks for confirmation before discarding those drafts; existing work stays selected without a milestone.

Opening creation from a release defaults new milestones to that release. Choose another value, including **No release**, in each milestone. New drafts must belong to a milestone and inherit its final release. Existing work keeps an assigned release; work without a release can inherit its selected milestone's release. The Feature itself has no release.

**Create Feature** saves the Feature, its milestone drafts, new Tasks/Bugs and existing-work assignments together. A failed save rolls back that hierarchy and task-number allocation and keeps the popup's input for correction. Cancelling creates no Feature, milestone, Task or Bug. Each milestone, existing-work and new-work list supports up to 100 items. Required fields on new Tasks/Bugs must have valid defaults; Feature custom-field choices do not propagate. Otherwise remove those drafts, create the work through its regular form and link it afterward. Labels retain their existing separate attachment workflow.

Creating a Feature requires **Features: Create**, and each new Task or Bug requires create permission for its kind. Creating milestones also requires **Milestones: Create**, and linking existing work requires update permission for its kind; setting a Milestone Lead requires assignment permission. Users without those permissions can create the Feature itself in this popup and add work through the regular forms. **Create more** clears the saved hierarchy before the next Feature. Changing project or item type asks before discarding a populated hierarchy while retaining the title and description.

API clients can supply optional Feature-only `featureComposition` to `POST /task/{projectId}`. It contains ordered `milestones` with local `key` values, `existingTasks` with `id`, `newTasks` with `title` and optional Task/Bug `type`, and optional `unassignedReleaseId`. Both work arrays may reference a `milestoneKey` or null. Invalid or duplicate references are rejected. `GET /task/feature-link-candidates/{projectId}` provides searchable, paginated eligible work with `feature:read` permission. Normal Task/Bug creation and bare Feature creation remain compatible.

Archive a Feature from its actions menu to move it to the library's archived view; unarchive restores it. Feature archive state is independent of workflow and does not archive milestones or child work.

### Link implementation work

Choose a Feature when creating or editing a Task/Bug, or add work in its Issues tab. A Task/Bug can belong to one Feature in the same project. Choose **No feature** or use **Remove from feature** to unlink it. Changing the Feature clears milestone membership while preserving the task's release. Features cannot own other Features and cannot be converted to or from leaf work.

Use [milestones](/core/functional/milestones) to plan stages of implementation. They carry execution metadata and appear in [Gantt](/core/functional/calendar-and-gantt#milestones). Selecting a milestone in the Feature sidebar opens and filters Issues; select it again to clear the filter. Milestone status is read-only and follows the statuses of its nonarchived linked Tasks and Bugs. Child progress follows workflow Done flags and keeps its existing counting rules.

### Feature workspace

Features have four tabs in both the side panel and full page. **Overview** opens by default. The header, properties, and milestone sidebar stay available while switching tabs.

- **Overview** keeps the description, latest published update, and resources together. Click the description to edit it with the shared document editor. Features have no Relations section.
- **Activity** combines official updates, comments, and system history, newest first. Choose **Comment** for conversation or **Update** to publish a note with **On track**, **At risk**, or **Off track** health. Updates capture each milestone's whole progress at publication and compare it with the previous report. Later milestone changes do not rewrite those snapshots.
- **Documents** holds named pages. Search or page through the list, then open a page: it fills the screen, and **All documents** or Esc returns to the list. Pages open ready to edit: type the title, press Enter to move into the text, and type `/` for headings, lists, tables, code, links, embeds, images, and files. Changes save automatically about a second after you stop typing, and the header shows **Saving…**, **Saved**, or **Couldn’t save** with **Try again**. **New document** creates an untitled page and opens it with the title selected. Deleting a page asks for confirmation. If another person saves first, saving pauses and your text stays while you review the latest revision, then keep your text or use theirs.
- **Issues** shows linked Tasks and Bugs grouped in workflow order, including completed work and items without a milestone. Use **Include archived** to show archived items. Creation and linking preserve the current Feature and selected milestone; removing an item from the Feature preserves the work itself.

Select a milestone in the sidebar to open Issues with that filter. Select it again to clear the filter, or choose **No milestone** to see work without a milestone. Filtering and pagination do not change Feature or milestone totals.

The selected tab and open document are included in the URL, so links, reload, and browser back/forward restore them. Opening a Feature from a release and switching to full-page view retains that release as the default for new milestones. Leaving a page first saves your latest changes and asks before discarding them only if that save fails; uploads and deletion in progress prevent dismissal. Leaving a description draft asks before discarding it. Uploaded files remain available while any surviving Feature description, document, update, or comment references them.

Publishing updates and creating or editing pages require **Features: Update**. Report authors may edit or delete their own reports; document deletion requires **Features: Delete**. Feature archiving keeps documents and reports. Native version 5 exports preserve pages and report snapshots, and imports continue to accept earlier formats.

### History and preservation

Feature history contains its comments and activity plus milestone lifecycle and planning changes. On upgrade, former Feature planning values are preserved in one immutable history snapshot before the fields are cleared. No milestones are created automatically. Existing task releases, milestone dates/order, and historical release progress remain intact.

**Delete feature** in the Feature's actions menu permanently removes the Feature with its milestones, documents, updates, and comments. Its Tasks and Bugs stay in the project with their planning fields, but without a Feature or milestone. Deleting from the full page returns you to the **Features** library. Duplicating creates an empty Feature without milestones. An empty Feature may move projects with its milestones. Task/Bug duplication preserves its existing Feature, milestone, release and estimate; the copy has no dates until a plan is applied or it is moved in Gantt.

### Subtasks from earlier versions

Earlier versions of Kaneo had subtasks. When your instance is upgraded, they are converted automatically:

- A top-level task that had subtasks becomes a feature, and its subtasks become its tasks.
- Deeper levels are flattened. A subtask of a subtask becomes a task of the top feature too, and its link to the subtask above it is kept as a **Related** relation.
- Other links that don't fit, such as a second parent or a link to a task in another project, are also kept as **Related** relations, unless a Feature is on either end: Features don't have relations, so those links were [removed](/core/operations/upgrades#features-lose-their-relations).

No task is deleted. Operators can find the details in [Upgrade Kaneo](/core/operations/upgrades#subtasks-become-features).

## Link related work

Open **Relations** and use the add button to find another task. Choose **Related** for a connection or **Blocks** when the current task must be resolved before the other one. The other task shows the inverse **blocked by** relationship.

Relations link Tasks and Bugs. Features don't have relations, so the picker doesn't offer them. To group work under a Feature, [link it](#link-implementation-work) instead.

Use **Remove relation** to unlink the tasks without deleting either task.

## Fill in custom fields

If your project defines extra fields, they appear under **Fields** in the task's **Properties** sidebar. In the side panel and when you create a task, they show as chips below status and priority. Click a field to set its value; a checkbox field toggles in place. Fields can hold text, numbers, dates, one or several dropdown choices, or a checkbox. A project manager defines the fields in [Custom fields settings](/core/functional/configure-workflows#set-up-custom-fields).

Required fields always keep a value, so they have no **Clear** option. If one is still empty when you create a task, Kaneo highlights it and tells you how many are missing.

## Delete a task

Use **Delete Task** only when you want to remove the task, rather than mark it done. Check the confirmation before proceeding. If deletion or assignment is unavailable, your workspace role may not permit it.

For work you want to keep but are not ready to start, use the [backlog](/core/functional/backlog-planning).
